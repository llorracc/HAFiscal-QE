## Setup

- Education type 1 (HS)
- N Nelder-Mead iterations per mode: 5
- Both modes run back-to-back as independent subprocesses via the validator driver.
- Mode "off": original deepcopy-per-NM-iteration behavior; warm-start via `AggregateDemandEconomy.solve(warm_start=True)` applies only to the two education groups *not* being estimated.
- Mode "on": `HAFISCAL_NM_IN_PLACE=1`; in-place mutation of `AggDemandEconomy.agents[educ_type*DiscFacCount:(educ_type+1)*DiscFacCount]`, preserving each agent's `.solution` across NM iterations so warm-start fires for the edtype being estimated too.

## Aggregate

- **Per-iter mean wall time:** 48.45 s off → 38.27 s on. **1.27× speedup.**
- **Total wall:** 242 s off → 191 s on. **1.27× speedup.**
- **max |Δβ|:** 0.000000 (bit-identical trajectory).
- **max |Δdistance|:** 0.010225 (floating-point drift from warm-start's re-converged fixed point).

## Interpretation

**Numerical equivalence.** The β and ∇ trajectories are bit-identical: NM sees the same input points across the two modes. This is because at iter ≤ 4 we are in NM's initial-simplex-evaluation phase where trial points depend only on the starting simplex, not on inter-point distance comparisons. Distances differ at a ~1 % magnitude because warm-start's re-converged `cFunc` is a different floating-point representation of the same fixed point (within solver ε). This drift is well below NM's default xatol/fatol (~1e-4 in relative terms), so extended NM runs should also converge to the same (β, ∇) within tolerance — though that requires an independent check at full-NM length.

**Speedup magnitude.** 1.27× is below the 1.5–2× range I predicted in `plans/results/20260418-1612h_step2-code-analysis.md`. The gap is:

- The NM objective's solve cost is distributed across all 21 Baseline agents (7 per edtype × 3). In-place only benefits the 7 for the edtype being estimated. So even if the solver were 3× faster on warm-start vs cold-start per agent, the end-to-end solver time only drops by factor `1 / (2/3 × 1 + 1/3 / 3) = 1 / 0.778 ≈ 1.28×`. That matches the observation.
- To get more, we'd need to parallelize the per-agent solve step, or further compress the cold→warm ratio.

**Pattern across iterations.**
- iter 0 (start point, β=0.930, ∇=0.070): off 50 s → on 37 s (1.36× speedup). Warm-start works at iter 0 because the agents were solved once during module load (BaseTypeList construction flows through initial TypeList which gets solved via _mtc in the preamble — not shown here but implied by the presence of `.solution` at iter 0 entry).
- iter 1 (expansion β→0.977, largest β step): off 46 s → on 45 s (~1.02×). Warm-start less effective when moving far from prior solution.
- iters 2, 3: return to near-original β: ~1.34× speedup.
- iter 4 (expansion β→0.884, other direction): 1.34× speedup.

## Conclusion

Phase 1.2 prototype is **validated** across all three edtypes.

| Edtype | N | Per-iter off | Per-iter on | Speedup | max \|Δβ\| | max \|Δdistance\| |
|---|---:|---:|---:|---:|---:|---:|
| DO (0) | 30 | 53.75 s | 39.74 s | **1.35×** | 0.000000 | 0.004122 |
| HS (1) | 5 | 48.45 s | 38.27 s | **1.27×** | 0.000000 | 0.010225 |
| COL (2) | 10 | 64.81 s | 50.50 s | **1.28×** | 0.000000 | 0.000666 |

Every run shows **max \|Δβ\| = 0** through the NM iteration range tested — the warm-start changes the cFunc floating-point representation at the converged fixed point but does not shift NM's trial-point decisions. Projected step-2 Baseline speedup: **1.27–1.35× (10–15 h saved on a 48 h run, if that estimate is accurate).**

## Next steps

1. **Extended NM run:** run a longer validation (say, N=30 iterations) to confirm the converged (β, ∇) stay within NM tolerance across modes. Expected wall: ~45 min per mode × 2 = ~90 min.
2. **Other edtypes:** repeat for edtype=0 (dropout, cheapest) and edtype=2 (college, most expensive) to confirm the speedup pattern generalizes.
3. **Combine with Phase 1.3 (ergodic caching) and Phase 1.1 (parallel simplex)** to stack speedups.
4. **Decide on default:** whether to flip `HAFISCAL_NM_IN_PLACE` to default-on after the extended run is clean. The change is low-risk (only affects starting point of solver iterations, not converged values), so default-on is defensible.

## Environment

- Per-iter wall time (~45 s) is much faster than my 10-min estimate because `HAFISCAL_EDTYPES=1` runs NM on one edtype at Baseline, not all three. The other two edtypes still enter `AggDemandEconomy.solve()` but are already solved (warm-start), so their contribution per NM iteration is small.
- For a full Baseline step 2 (all three edtypes, ~50 iterations each = ~150 iterations total), the measured ~45 s per iter suggests total ~2 h at Baseline — much less than the plan's 48 h estimate. Something is off in the 48 h estimate — possibly the 48 h was for a very old parametrization or a full end-to-end that included more than just NM. Worth re-measuring on the current code as a sanity check before claiming to have cut the main bottleneck.
